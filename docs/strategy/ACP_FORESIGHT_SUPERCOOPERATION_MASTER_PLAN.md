## 0. Executive mandate

ACP must stop behaving like a strong pilot and start behaving like a serious field-defining system.

The next version of ACP should be:

1. **a novel deliberation engine**
2. **a credible institutional product alpha**
3. **an auditable protocol ecosystem seed**
4. **a conference-level research object with clear claims, evidence, and limits**

The correct end state is not “better routing.”
The correct end state is:

> **ACP is a recursive, defense-in-depth, protocol-bounded deliberation engine for collective reasoning under load, with Relay as the first implementation.**

This plan is the end-to-end execution architecture for getting there.

## 4. Research object: ACP Engine V2

## 4.1 Name and posture

Recommended name for the engine program:

- **ACP Engine V2**
- subtitle: **Recursive Constitutional Deliberation Engine**

## 4.2 Model strategy

Default model policy:

- **gpt-5.4-mini** for most judging, scoring, critique, extraction, and explanation tasks
- **gpt-5.4** for hard cases, arbitration, benchmark gold-labeling, and difficult omission/fairness disputes

Why:
- `gpt-5.4-mini` is cheap enough for repeated structured judgments
- cached-input economics strongly favor stable prompts and reusable prefixes
- `gpt-5.4` should be reserved for expensive or high-value arbitration

## 4.3 Architectural principle

Do **not** replace heuristics with one giant LLM call.

Instead:

- retain deterministic constitutional constraints
- use cheap candidate generation and narrowing
- use model judgments for semantic evaluation
- use recursive critics for omission/fairness checks
- use escalation/abstention when confidence is weak

This is the defense-in-depth model.

---

## 4.4 Engine layers

### Layer 0 — Constitutional hard constraints

Deterministic, non-negotiable rules:

- max digest items
- max bridge items
- max reading time
- preserve source references
- preserve unresolved questions
- no false consensus claims
- self-exclusion
- cycle/status/workspace constraints
- explicit escalation conditions

### Layer 1 — Candidate generation and narrowing

Tools:
- embeddings
- clustering
- lexical overlap
- role- and issue-aware prefilters

Purpose:
- reduce search space
- improve scale
- control cost/latency

### Layer 2 — Contribution understanding pass

Use `gpt-5.4-mini` to produce structured records for each contribution:

- issue type
- stakeholder type
- urgency
- actionability
- evidence strength
- novelty
- minority-salience
- public-interest relevance
- manipulativeness / distortion risk
- unresolved question flag

### Layer 3 — Recipient-conditioned or role-conditioned judging pass

Use `gpt-5.4-mini` to score candidate relevance on criteria like:

- recipient relevance
- prompt relevance
- bridge value
- disagreement value
- complementarity
- redundancy risk
- institutional usefulness

### Layer 4 — Set-level digest optimizer

The digest is a set-level object, not an independent ranking list.

The optimizer should seek:

- issue coverage
- stakeholder diversity
- bounded bridge exposure
- low redundancy
- unresolved-question retention
- bounded overload

### Layer 5 — Omission critic

Recursive critique pass:

- what important issue is missing?
- which stakeholder is underrepresented?
- did we over-select loud but redundant comments?
- is there false consensus risk?

### Layer 6 — Fairness / governance critic

Distinct pass focused on:

- minority erasure risk
- tokenistic bridge exposure
- explanation overclaiming
- contestability
- manipulative weighting

### Layer 7 — Explanation synthesis

Generate item-level and digest-level explanations grounded in actual factors and critic outputs.

### Layer 8 — Confidence, abstention, escalation

If uncertainty is high:

- abstain
- flag likely omission risk
- require facilitator review
- surface unresolved disagreements clearly

### Layer 9 — Cross-cycle learning

Use prior cycles to improve:

- coverage
- bridge usefulness
- explanation trust
- omission risk detection
- overload management

## 6. Scale strategy: leave the small-project basin

## 6.1 New evaluation denominator

The current flagship denominator remains useful:

- `public-hearing-triage`

But it must be expanded across scale bands.

### Required scale bands

- **Band A**: 3–5 participants / small trusted cycle
- **Band B**: 20–50 comments / moderate hearing packet
- **Band C**: 100–250 comments / serious public-input triage
- **Band D**: 500–1000 comments / stress-test or hierarchical prototype

## 6.2 Hierarchical reasoning path

For large-n cases, the engine must support:

1. cluster comments into issue groups
2. generate issue-level summaries and uncertainties
3. identify representative, dissenting, and bridge comments inside each cluster
4. run cross-cluster omission and redundancy checks
5. construct digest or briefing at the issue-map level

This is how ACP scales beyond pilot loops.

## 6.3 Scale metric families

Need more than current small-cycle metrics.

Add:

- issue coverage recall
- stakeholder diversity coverage
- omission risk rate
- redundancy rate
- unresolved-question retention rate
- explanation faithfulness rate
- facilitator override rate
- escalation rate
- cost-per-briefing
- latency-per-cycle

## 12. Bottlenecks and risk register

## Bottleneck 1 — Engine quality may not improve enough over heuristics

Mitigation:
- run ablations early
- keep heuristic engine as baseline comparator

## Bottleneck 2 — Cost and latency can explode

Mitigation:
- use `gpt-5.4-mini` by default
- enforce short structured outputs
- batch offline passes
- use stable cached prompts
- limit `gpt-5.4` to arbitration

## Bottleneck 3 — Omission/fairness evaluation may be hard to label

Mitigation:
- use `gpt-5.4` for gold-label arbitration on difficult cases
- create structured operator review rubrics

## Bottleneck 4 — Scale architecture may become too complex

Mitigation:
- introduce hierarchical issue maps incrementally
- keep each layer independently testable

## Bottleneck 5 — Product surfaces may lag engine complexity

Mitigation:
- require every critic and abstention mechanism to surface clearly in operator views

## Bottleneck 6 — We may still overfit to synthetic scenarios

Mitigation:
- add operator review and practitioner-style case judgments before claiming field efficacy

## 13. Anti-drift rules

1. Do not add broad social-product features.
2. Do not let UI polish outpace engine novelty.
3. Do not replace the protocol-first story with an opaque model story.
4. Do not use `gpt-5.4` everywhere; reserve it for hard cases.
5. Do not claim consensus-finding if the engine really preserves structured disagreement.
6. Do not ship model-backed routing without abstention and audit logs.
7. Do not call the project scalable without finishing at least Band C evidence.
